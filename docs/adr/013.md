# ADR-013: Protocol and runtime refinements

Status: Accepted for implementation; review alongside provider compatibility evidence.

The handoff leaves details requiring concrete wire and operational contracts. These choices preserve its correctness boundary:

- Claims have no installation ID yet; the signed installation component is the literal `claim`. A one-use pairing code binds organization, store and mode. Failed-response recovery requires the same public-key identity.
- Woo batches add `scan_id`, one-based `page`, and `final_page`. Pages have semantic hashes independent of request timestamp/signature. A contiguous acknowledged final page proves coverage; a partial scan cannot advance it.
- Orders include authoritative `refund_ids`. Removed Woo refunds cease to participate in the current snapshot while previous immutable observations remain available.
- Five-minute scheduled polling provides margin below the fifteen-minute freshness ceiling. Woo uses a two-minute extraction cutoff to tolerate source timestamp granularity and update races. NFR latency still requires measurement.
- Known instant methods use the instant grace; unknown methods use the longer asynchronous grace. Custom financial statuses and unverified gateway variants remain unsupported.
- A duplicate payment is considered corrected only when every excess successful intent is fully refunded in the same currency, refund grace and shared coverage have passed, and exactly one payment remains retained. These compensating refunds are excluded from the retained order's refund comparison. Partial, pending or over-refunds cannot establish correction.
- Minimal external JavaScript implements mutation forms and idempotency. The handoff's HTMX preference is a SHOULD; a framework dependency is unnecessary for these forms. Server-rendered reads remain available and authorization stays on the server.
- OAuth and email provider commits cannot be made atomic with PostgreSQL. Refresh uncertainty requires re-consent; SES ambiguity can repeat delivery. Operator instructions disclose both windows.
- A separate durable S3 erasure receipt is written before database erasure commits. Restore procedures replay it before ingress is reopened, preventing backup restoration from reinstating erased data.
- Plugin signing-key and Stripe webhook-secret rotation permit at most a twenty-four-hour overlap. Pending plugin rotation material is retained across an uncertain response.

Implementations must not broaden this record into permission for financial writes, payload retention or deployment without environment approval.

Amount at risk is an affected transaction amount for payment/identity disagreements (PI-005 and PI-010), not a forecast of loss. Refund aggregate differences use the difference; duplicate-success findings report the affected order amount. Reports do not add different currencies together.
